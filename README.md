# Авиапульс

Кабинет аналитика для кейса «Динамическое ценообразование авиабилетов». Пользователь выбирает города, дату и цену. Django пересчитывает девять квантилей готового ML-прогноза, продажи и ожидаемые свободные места. Модель не обучается, бронирования и оплаты нет.

## Стек

Python 3.12, Django **5.2.19**, PostgreSQL **17.12**, Django ORM/миграции/Templates, обычный JavaScript, локальный Plotly.js **3.3.0**, Gunicorn **27.0.1**, Caddy **2.11.9**, Docker Compose. Django закреплён на актуальном security-patch ветки 5.2: [официальный выпуск](https://www.djangoproject.com/weblog/2026/nov/03/security-releases/).

## Быстрый локальный запуск

Нужны Docker с Linux-контейнерами и Docker Compose. Все команды ниже выполняются **из корня репозитория**. Устанавливать Python на хост для Docker-запуска не требуется.

1. Создайте `.env` из `.env.example`: PowerShell `Copy-Item .env.example .env`, Linux/macOS `cp .env.example .env`.
2. Замените `DJANGO_SECRET_KEY` и `POSTGRES_PASSWORD` случайными значениями. Ключ Django — минимум 32 символа, рекомендуется 50+. Секреты не включены в репозиторий.
3. Выполните:

```sh
docker compose build web
docker compose up -d db
docker compose run --rm web python manage.py migrate --noinput
docker compose run --rm web python manage.py import_forecast --forecast data/my_forecast.csv --routes data/routes.csv
docker compose run --rm web python manage.py collectstatic --noinput
docker compose up -d
```

Откройте **http://localhost:8080**. Калькулятор доступен гостям. Кнопки регистрации и входа в верхней панели работают через штатную систему Django. Обычная регистрация не даёт доступа в админку.

Остановка: `docker compose down`. Версии данных и аккаунты остаются в томе PostgreSQL. Следующий запуск: `docker compose up -d`. Команда `down -v` удаляет тома и данные, для обычной остановки её использовать не нужно.

## Данные и импорт

В `data/` включены **реальные** `my_forecast.csv` и `routes.csv` из выполненной ML-части: пять направлений из Москвы, 155 прогнозов на **1 июня — 1 июля 2026**, 1 395 квантилей. Даты показываются из БД; текущая календарная дата их не блокирует. Заглушка `seasonal_forecast.csv` в приложении не используется.

Справочник исходного кейса: [routes.csv](https://gist.githubusercontent.com/Murkat-git/3ddc868889d3e0d37542d786c8b1aa74/raw/routes.csv). Источник `my_forecast.csv` — наш прогноз «компактный календарь + SMA/EMA», экспорт задания 7 ML-ноутбука. Сам ноутбук, AutoGluon и файлы моделей приложению **не нужны**.

Повторный импорт:

```sh
docker compose exec web python manage.py import_forecast --forecast data/my_forecast.csv --routes data/routes.csv
```

Команда проверяет заголовки, даты, конечность и точность чисел, вместимость, чувствительность, дубли, девять квантилей и их порядок. Ошибка указывает файл, строку и колонку. Пересечения квантилей не исправляются.

Вариант с новыми файлами: поместите их в `data/`, пересоберите образ (`docker compose build web`), затем выполните команду импорта через `docker compose run --rm web ...` и `docker compose up -d`. Можно также скопировать CSV в работающий контейнер командой `docker compose cp`, указав соответствующий путь в `--forecast`/`--routes`.

Каждая пара содержимого CSV получает SHA-256 и версию. Одинаковые файлы не создают дубликаты; повторный импорт старого набора активирует его версию. Параметры маршрутов хранятся в снимке версии и связанных типизированных `ForecastRouteParameters`: денежные поля — DecimalField. Дополнительные числовые параметры сохраняются в JSON десятичными строками. Названия исходных файлов тоже сохранены.

Импорт выполняется одной транзакцией. Advisory lock PostgreSQL сериализует конкурирующие импорты, уникальные ограничения запрещают повторную пару файлов и две активные версии. Новая версия публикуется после записи всех прогнозов; при сбое старая остаётся активной. Запрос расчёта использует одну выбранную версию, даже если во время запроса прошёл импорт. CSV не читаются при пользовательских запросах.

Для пяти кодов город задан явно в `forecast/services/importer.py`, `ROUTE_CITIES`. Неизвестный код требует проверенного дополнения словаря; название маршрута не разбивается по символам.

## Расчёт

Для каждого уровня `q`:

```text
demand_q = base_demand_q − price_sensitivity × (price − base_price)
median_demand = demand_0.5
sales = min(seats, max(0, median_demand))
free_seats = seats − sales
load_factor = sales / seats, либо 0 при seats = 0
```

Расчёт находится в `forecast/services/calculation.py`. Используется Decimal, без округления до целых билетов. Все квантили рассчитываются одной функцией; медиана карточки берётся из того же списка, который получает график. В интерфейсе прогнозы показываются с одним знаком после запятой.

По умолчанию карточка спроса и девять точек графика показывают `max(0, demand_q)`: отрицательное количество пассажиров на основном экране не выводится. Переключатель **«Исходная формула»** одновременно переводит карточку и график в исходные линейные оценки, в том числе отрицательные. В обоих режимах медиана карточки совпадает с точкой 50%; продажи рассчитываются одинаково и не бывают отрицательными. Так сохранён проверяемый расчёт из задания, а основной интерфейс показывает физически осмысленный спрос.

API сохраняет исходные `median_demand`/`quantiles` для совместимости и проверки формулы. Дополнительные `nonnegative_median_demand`/`nonnegative_quantiles` предназначены для основного режима интерфейса. Спрос не ограничивается вместимостью. Колонки `*_price_demand` из CSV тоже не считаются готовыми продажами. Рекомендуемые `price_min`/`price_max` показываются как подсказка, а не ограничение цены.

Свободные места — **прогноз**, не реальный остаток бронирования. График соединяет девять квантилей, выделяет медиану и вместимость. Это не плотность распределения; заявленное покрытие квантилей зависит от качества ML-модели. Мы не гарантируем калибровку: в майской диагностике номинальный 80%-й интервал покрывал около 96% факта.

## API

Гостевые API, без REST Framework:

- `GET /api/routes` — направления активной версии, базовые/рекомендуемые цены, период и версия.
- `GET /api/routes/MOW-AER/dates` — доступные даты и вместимость.
- `POST /api/forecast` — JSON: `origin`, `destination`, `date`, `price`.

Пример тела:

```json
{"origin":"Москва","destination":"Сочи","date":"2026-06-12","price":"9500.25"}
```

Backend сам разрешает направление и повторно проверяет ввод. Денежные/прогнозные десятичные значения возвращаются строками, чтобы не терять точность JSON-чисел. Ответ содержит маршрут, дату, цену, базовую цену, вместимость, `median_demand`, `sales`, `free_seats`, `load_factor`, девять `quantiles`, статус интерпретации и ID/дату импорта версии.

Ошибки — JSON с `error.message` и при необходимости `error.fields`: 400 неверный ввод, 404 отсутствующий маршрут/дата, 503 данные или БД недоступны. Также 403 при отсутствии корректного CSRF и 405 при неверном методе. Для POST нужны cookie сессии формы и заголовок `X-CSRFToken`; JavaScript получает токен из скрытого поля формы. Пароли/токены в localStorage не хранятся.

Технический диапазон цены — неотрицательные числа, представимые конечным ненулевым значением IEEE 754 binary64, и ноль. Это ограничение представимости графика и защиты от огромных десятичных экспонент, **не** рекомендуемый ценовой диапазон маршрута. Например, 100 000 ₽ и `1e100` принимаются, `NaN`, `Infinity`, `1e100000000` и ненулевые значения с полным underflow — JSON 400. Арифметика внутри остаётся Decimal; float используется только для проверки представимости. Нулевая цена с любой экспонентой точно приводится к 0 без разворачивания миллионов нулей.

## Администратор

```sh
docker compose exec web python manage.py createsuperuser
```

Админка: http://localhost:8080/admin/. Прогнозы, квантили, параметры и версии доступны для чтения с поиском и фильтрами. Создание/редактирование/удаление импортированных записей через admin запрещены; обновление — только командой импорта. Администратор создаётся отдельно, его пароля в проекте нет.

## Проверки

```sh
docker compose run --rm web python manage.py test forecast accounts -v 2
docker compose run --rm web python manage.py makemigrations --check --dry-run
docker compose run --rm web python manage.py check
docker compose ps
```

Проверка 15 расчётов на реальных CSV через работающий API (на хосте нужен только Python): `python scripts/verify_running.py http://localhost:8080`. Она не заменяет браузерный тест.

Содержательные тесты проверяют формулу и дробную точность, ограничения только продаж, нулевую вместимость, совпадение медианы и графика, API/CSRF, неверные данные, идемпотентность, снимки параметров, откат сбоя импорта, ограничение одной активной версии и полный цикл регистрации/входа/выхода с хешированием пароля. Тесты работают на **PostgreSQL**, не SQLite. Синтетические данные находятся исключительно в тестах.

Проверены сборка Docker, миграции, импорт реальных CSV, **20 тестов на PostgreSQL**, 15 расчётов через работающий API и сохранность данных после перезапуска.

Для ручной проверки: откройте страницу, смените маршрут/дату/цену, нажмите «Рассчитать», сопоставьте медиану карточки с точкой 50% и подсказкой, проверьте цену 0, высокую цену с отрицательным спросом, пустую/отрицательную цену. Убедитесь, что при изменении полей старый результат скрывается. Проверьте регистрацию/вход/POST-выход и ширину экрана около 390 px. После остановки/старта Compose проверьте сохранность версии и аккаунта.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `DJANGO_SECRET_KEY` | Секрет Django; обязателен, не менее 32 символов |
| `DJANGO_DEBUG` | В рабочем запуске False |
| `DJANGO_ALLOWED_HOSTS` | Список хостов через запятую |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Полные адреса с протоколом, через запятую |
| `DJANGO_SECURE_COOKIES` | True при HTTPS, False локально по HTTP |
| `DJANGO_SSL_REDIRECT` | Перенаправлять HTTP на HTTPS; локально False |
| `DJANGO_HSTS_SECONDS` | HSTS после настройки рабочего HTTPS; по умолчанию 0 |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | БД и учётные данные |
| `POSTGRES_HOST`, `POSTGRES_PORT` | В Compose принудительно db:5432 |
| `SITE_ADDRESS` | `:80` локально, публичный домен для HTTPS |
| `BIND_ADDRESS` | 127.0.0.1 локально; 0.0.0.0 только при публикации |
| `HTTP_PORT`, `HTTPS_PORT` | 8080/8443 локально; 80/443 при публикации |

## Production

Для размещения в Amvera подготовлены `amvera.yml`, отдельные настройки статики и автоматический старт: [инструкция](deploy/AMVERA.md).

Сравнение бесплатных вариантов на 10 дней и ограничений рекомендованного в PDF Timeweb — в [deploy/HOSTING.md](deploy/HOSTING.md). Исследование хостинга не означает, что сайт уже опубликован.

Публикация и платные услуги не выполнялись. Для собственного сервера:

1. Направьте DNS домена на сервер, откройте 80/443.
2. В `.env` задайте длинные уникальные секреты, `SITE_ADDRESS=airfare.example.org`, `BIND_ADDRESS=0.0.0.0`, `HTTP_PORT=80`, `HTTPS_PORT=443`.
3. `DJANGO_ALLOWED_HOSTS=airfare.example.org,localhost,127.0.0.1`, `DJANGO_CSRF_TRUSTED_ORIGINS=https://airfare.example.org`, `DJANGO_DEBUG=False`, `DJANGO_SECURE_COOKIES=True`, `DJANGO_SSL_REDIRECT=True`.
4. Повторите команды сборки, миграций, импорта и `collectstatic` из локального запуска. После настройки HTTPS можно включить HSTS.
5. `docker compose exec web python manage.py check --deploy` и проверка через HTTPS.

Caddy автоматически получает/обновляет сертификат для домена, проксирует Gunicorn и раздаёт `collectstatic` из общего тома. TLS-данные и PostgreSQL лежат в постоянных томах. `/health` исключён из HTTPS-перенаправления для внутреннего healthcheck. БД и Gunicorn не публикуют порты наружу. Импорт и миграции не выполняются в каждом worker.

Логи: `docker compose logs --tail=100 web proxy db`. Резервную копию PostgreSQL делайте `pg_dump` из контейнера; `.env` и том БД необходимо сохранять между развёртываниями.

## Сдача по условиям кейса

Это вариант **C: веб-интерфейс с backend API**, с графиком, регистрацией и авторизацией. Открытый GitHub-репозиторий заменяет ZIP с кодом. Для проверки функций нужна либо ссылка на работающий сайт, либо видео всех функций на локальном компьютере. При выборе видео дополнительный пункт за хостинг не засчитывается.

Ссылку на репозиторий и остальные материалы нужно положить в доступную для жюри папку с ФИО на Google или Яндекс Диске. Сдаваемые файлы подписываются ФИО. ML-ноутбук и его CSV сдаются отдельно; здесь находятся веб-приложение и необходимые ему данные.
